# Afterframe → Wan LoRA: "Sora 2 video, prompt:" fine-tuning on Kaggle 2 × T4

This is an end-to-end pipeline. It extracts prompt-paired videos from the Afterframe archive, builds a
deduplicated and provenance-flagged dataset, and LoRA-fine-tunes an open-weight text-to-video model on
Kaggle's free 2 × Tesla T4. Every caption is `Sora 2 video, prompt: <original backend prompt>`.

## Phase 1: what the site exposes

Afterframe is a Sites-Worker app (`/afterframe-sites.js`). Endpoints, all checked by hand:

```
POST /api/session                 visitor session -> {"id", "admin", ...}       (the page makes this call on every load)
GET  /api/post-count              {"posts": 7706}
GET  /api/docs/posts?details=1&sort=created&direction=desc&limit=..&after=<id>&afterCreated=<ms>
                                  50 rows per page + cursor
GET  /api/post-prompt/<id>        {"prompt": ...}   OWNER ONLY (403 not_granted for visitors)
GET  /media/<asset-uuid>          original uploaded bytes, Range supported
```

Public post fields: `asset, by (uploader visitor id), created, w, h, dur, name, title, cap, remixOf,
like/comment/remix/reportCount, thumb, type`. Uploads store the prompt from the user's Sora export as
`exportPrompt`, which the API returns only to the owner. The extractor makes only GET requests, plus the
session POST that the page itself makes. A test asserts it never sends a write.

What the scan shows:
- 23.95 h of video in total; 704×1280 (4,674) and 1280×704 (2,906) dominate; 74.6 % of posts are 9.5–11 s and 20.9 % are ≥ 14.5 s; all MP4.
- 91 distinct uploaders. One uploader accounts for 65.5 % of posts.
- 7,342 filenames carry a Sora generation id (a ULID). The ids date from 2025-01-08 to 2026-04-28, and 7 predate the Sora 2 launch.
- 68 generation ids appear more than once; these are re-uploads, handled by dedup.
- In the 12-video sample, every file was 30 fps with an audio track. 10 of 12 carried a C2PA manifest signed by an OpenAI "Truepic Lens CLI in Sora" certificate (`softwareAgent: Sora`, `trainedAlgorithmicMedia`); 2 had none.
- Mean file size is 6.8 MB, so the full archive is about **52 GB** (16 hash shards of about 3.3 GB each).

## Running extraction (owner)

```bash
pip install -r requirements.txt
# 1. catalog (public)
python extract_afterframe.py scan --out afterframe_data
# 2. prompts: sign in as owner in a browser (Settings → Owner sign-in), copy the request Cookie header
#    for afterframe.marcelalia2.chatgpt.site from devtools into a file
python extract_afterframe.py prompts --out afterframe_data --cookie-file owner_cookie.txt
# 3. download, in increments: choose WHICH uploads you may train on
python extract_afterframe.py download --out afterframe_data --cookie-file owner_cookie.txt \
       --permission-policy owner-uploads --uploader-id <your 64-hex visitor id> \
       --num-shards 16 --shards 0,1,2,3 --max-gb 15 --deep-verify
#    --permission-policy allowlist --uploaders-file permitted.txt   (uploaders who granted permission)
#    --permission-policy all-attested                                 (you hold rights to every upload)
# 4. dataset
python prepare_dataset.py --data afterframe_data --out dataset --permission-policy owner-uploads --uploader-id <id>
python extract_afterframe.py status --out afterframe_data
```

Every stage resumes after an interruption. The scan cursor, prompt and download records are append-only
JSONL; partial files resume via Range. Rerunning `scan` later only fetches new posts.

**Eligibility:** a non-empty backend prompt (after whitespace stripping), a permitted uploader, a media
asset, not hidden by moderation, and a download that is verified and not a duplicate. Prompts are never
generated, inferred, rewritten or substituted. The prompt string is copied byte for byte.

## Phases 2 and 3: captions and dataset

- `caption = "Sora 2 video, prompt: " + backend_prompt`, built and asserted in one function. The caption file
  (UTF-8, no trailing newline), the manifest's `training_caption`, and prefix + `backend_prompt` must agree.
  The trainer refuses a shard where they don't. The cache step checks that the prefix's tokens survive
  tokenisation and records any truncation beyond 512 tokens; truncation cuts only the tail. The cached text
  embedding is of the full prefixed caption. umT5 sees it after diffusers' `prompt_clean` (ftfy plus
  whitespace collapse), exactly as at inference.
- **Provenance labels:**
  - `sora2_confirmed_by_backend`: only if the backend ever returns a model field naming Sora 2.
  - `sora2_likely`: an OpenAI/Sora C2PA claim, plus a generation date after 2025-09-30, an audio track and a Sora 2 resolution.
  - `sora_version_uncertain`: a Sora C2PA claim, but at least one of those traits is missing.
  - `provenance_uncertain`: no Sora C2PA claim.
  - `other_model_by_backend`: excluded by default.

  The C2PA claims are parsed but **signatures are not cryptographically validated**; run `c2patool` for that. Add
  `--exclude-provenance provenance_uncertain` for a stricter dataset.
- **Dedup and leakage:** posts are merged into one group when they have the same SHA-256 or Sora generation id,
  or when their perceptual signatures match. A signature is a 64-bit dHash per frame at 4 fps, and matching
  tolerates re-encoding, rescaling and trims. By default, byte-identical prompts are grouped too. One copy
  per duplicate group is kept, and whole groups go to train or val (an assertion checks this). On real
  samples, re-encoded, trimmed and offset copies matched at 0.9–1.0, while unrelated videos peaked at 0.4;
  the threshold is 0.6.
- **Quality flags** (recorded, some excluding): `low_resolution`, `too_short`, `unusual_fps`, `nearly_static`, `mostly_dark`.
- **Layout:** `dataset/shard_XXX/{videos,captions,manifest.jsonl}` hard-links the original bytes. The
  untouched original dataset stays in `afterframe_data/raw/`, and training clips exist only as cached
  latents. Each shard folder is self-contained, so it can be its own Kaggle dataset.

## Phase 4: base model choice

| Model | Fits LoRA training on one 16 GB T4? | Verdict |
|---|---|---|
| **Wan2.1-T2V-1.3B** | Yes. 2.8 GB fp16 weights, fp16-safe modules kept fp32 by diffusers, small enough for DDP replicas | **Default.** Strong motion and prompt adherence for its size; supported by diffusers and peft |
| **Wan2.2-TI2V-5B** | Probably, at ≤ 480p. About 10 GB fp16 weights per GPU, but its 16×16 VAE means 4× fewer tokens than Wan2.1 at equal resolution, so 352p/49 frames needs about 1.5× the FLOPs of 1.3B at 288p | **`wan22_5b_experimental` preset.** Better base quality; the notebook's smoke test is the go/no-go (fp16 stability and memory are unverified) |
| HunyuanVideo 1.5 (8.3B) | No without quantization or offload. 16.6 GB of fp16 weights alone exceed a T4 | Inference on 16 GB needs offloading ([LTX VRAM guide](https://ltx.io/blog/open-video-model-vram-requirements)); no published 16 GB training figure found |
| LTX-2 / 2.5 | No. The official trainer recommends 80 GB; its low-VRAM INT8 mode targets 32 GB | Not trainable on a T4 |
| CogVideoX-2B/5B | Yes | Older; weaker motion than Wan at similar cost |
| Wan 14B / A14B, Mochi 10B | No | Too large |

Inference and training compatibility differ: several models *run* on 16 GB with offloading but cannot
*train* there. Kaggle's two T4s are two 16 GB devices, so the 32 GB never pools; the pipeline uses DDP and
needs the model to fit on each GPU. Sources: [Wan2.2-TI2V-5B-Diffusers](https://huggingface.co/Wan-AI/Wan2.2-TI2V-5B-Diffusers),
[AMD Wan2.2 fine-tuning notes](https://rocm.blogs.amd.com/artificial-intelligence/finetuning-wan-part1/README.html),
[open-model VRAM survey](https://ltx.io/blog/open-video-model-vram-requirements),
[open video models 2026](https://www.thundercompute.com/blog/best-open-source-ai-video-generation-models).

## Phases 5 and 6: training design

- **2 × T4:** `torchrun --nproc_per_node=2`. Each rank holds a frozen fp16 base model and fp32 LoRA weights;
  only LoRA gradients are all-reduced, with `no_sync` during gradient accumulation. The models load one rank
  at a time, straight onto the GPU, to keep within Kaggle's RAM. NCCL P2P is off by default.
- **T4-safe numerics:** fp16 autocast plus `GradScaler`; no bf16 (refused). SDPA uses its mem-efficient and
  math kernels, and flash is disabled on sm < 80. Non-finite steps are skipped on all ranks.
- **Memory:** gradient checkpointing (non-reentrant), gradient accumulation, bitsandbytes `AdamW8bit` (falls
  back to AdamW), and VAE tiling. Training loads only the transformer; umT5 and the VAE are used only at cache time.
- **Caching:** text embeddings once per unique caption; latents per stage, aspect bucket and frame bucket.
  Clips are decoded by ffmpeg straight to the bucket (fps resample, cover-resize, centre crop), with
  decoding overlapped with VAE encoding. The VAE `auto` mode encodes the first clip in both fp16 and fp32 and
  keeps fp16 only if the relative error is < 2 %.
- **Buckets and variable length:** landscape, portrait and square buckets per stage. Each video gives up to
  `clips_per_video` non-overlapping windows, plus a shorter tail window when one fits.
- **Progressive resolution:** a preset's stages run low to high resolution. Each stage covers a
  `shard_fraction` of shards, so expensive 480p stages don't consume the whole quota.
- **Resumable everywhere:** atomic checkpoints (LoRA, optimizer, scaler, scheduler, data position, RNG). Training
  stops on a time budget and resumes at the same batch next session. `plan_state.json` records which
  shard chunks each stage has finished, and checkpoints can be mirrored to a private HF repo.
- **Validation:** held-out flow-matching loss with fixed noise and timesteps, plus periodic sample videos
  from unseen prompts.
- **Export:** `afterframe_sora2_lora.safetensors` in diffusers/peft keys, with alpha/rank folded into `lora_B`
  so strength 1.0 matches training, plus `_comfyui.safetensors` with original Wan key names.

**Disk:**
- Raw archive: about 52 GB, 3.3 GB per shard.
- Text embeddings: about 1.6 MB per caption at 200 tokens (fp16, unpadded).
- Latents: shown in the table. A 480-video shard with 2 clips per video is about 0.6 GB at 288p, 1.4 GB at 352p and 4 GB at 480p.

The cache lives in `/tmp`, is rolled shard by shard, and is deleted after each chunk is trained. Only
checkpoints, logs and LoRA files go into `/kaggle/working`.

**GPU hours for `balanced`, if all about 7,500 videos were eligible** (≈ 15k clips per full stage):

| Part | Estimate |
|---|---|
| 288p stage on half the shards (7.5k clips × 3–5 s) | 6–10 GPU-h |
| 352p stage on all shards (15k clips × 10–17 s) | 42–71 GPU-h |
| VAE caching (22.5k clips × 2–8 s) | 12–50 GPU-h |
| **Total** | **60–130 GPU-h** |

On 2 GPUs that is **30–65 wall-clock hours, so 3–6 Kaggle sessions** spread over about 1–2 weeks of
Kaggle's weekly GPU quota. The real eligible count is unknown until prompts are fetched. `low_memory`
needs about a quarter of this, and `max_quality` about twice as much.

## Kaggle workflow

1. Upload each `dataset/shard_XXX/` as a Kaggle dataset (or use notebook §4 to extract shards inside Kaggle
   with the owner cookie in Kaggle Secrets). Attach them, then set Accelerator to *GPU T4 x2* and Internet to *On*.
2. Run all. §7's smoke test must print `SMOKE TEST PASSED`, and §8 prints measured speed, memory and a
   GPU-hour estimate. §10 then trains until about 25 min before the 12 h limit.
3. *Save Version*. For the next session, attach the previous version's output as an input, and §9 restores
   the run. Alternatively set `HF_REPO` and the `HF_TOKEN` secret.
4. §11 plots loss, LR and memory; §12 shows validation videos; §13 exports the `.safetensors`.
5. §14 runs inference from unseen prompts at adjustable LoRA strength, seed, size, frame count, guidance and
   steps. It shows base vs LoRA side by side at the same seed, plus a strength sweep. From the CLI:
   `python afterframe_wan.py infer --lora afterframe_sora2_lora.safetensors --compare-base --prompt "Sora 2 video, prompt: ..."`.

## Before you train or publish

- **Permissions:** Afterframe accepts uploads from any visitor (91 uploaders so far). Hosting a post doesn't
  grant you training rights to it, which is why `--permission-policy` is mandatory.
- **OpenAI terms:** these are Sora outputs. OpenAI's Terms of Use restrict using Output to develop models
  that compete with OpenAI. Check how that applies to you before training on or releasing anything built
  from them.
- **Watermarks and provenance:** most clips carry the moving Sora watermark and a C2PA manifest. A LoRA
  trained on them will probably learn to draw a Sora-like watermark, which would make your model's output
  look like genuine Sora output. The pipeline deliberately does not strip watermarks. Label generated
  videos as made with your fine-tuned Wan model. Publishing the model under the "Sora" name may also raise
  trademark issues.
- **People:** Sora 2 "cameos" depict real people. Consider excluding or reviewing videos of identifiable
  people before training.
